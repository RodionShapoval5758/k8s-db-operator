# ADR 0001: Hand-roll the controller scaffold instead of using kubebuilder

## Status

Accepted

## Context

This repository is a take-home exercise graded on "200 lines you can defend"
rather than volume or conformance to a particular tool's conventions
(`README.md`). The operator itself is small in scope: one CRD
(`ManagedDatabase`), two spec fields (`engine`, `sizeGB`), a handful of
status fields, no webhooks, a single API version, and no requirement to run
in-cluster — the README explicitly allows and expects the controller to run
locally (`go run`) against the kind cluster, with no container image needed.

kubebuilder's default scaffold generates a full in-cluster-deployment project
regardless of scale: CI workflows, a devcontainer, lint config, an e2e test
harness, Prometheus/metrics RBAC, a `Dockerfile`, kustomize overlays for an
in-cluster `Deployment`, and generated docs — roughly 30 files, most serving
capabilities this exercise doesn't use, since the controller runs
out-of-cluster.

## Decision

Scaffold the operator by hand instead: a plain `go.mod`; `api/v1alpha1/types.go`
holding `Spec`/`Status` and scheme registration; a hand-written
`api/v1alpha1/zz_deepcopy.go` implementing `runtime.Object`; a minimal
`cmd/main.go` wiring `ctrl.NewManager` to the reconciler;
`internal/controller/manageddatabase.go` holding the `Reconciler`; and a
hand-written `config/crd.yaml` (OpenAPI schema + printer columns) in place of
one generated by `controller-gen`.

No kubebuilder, no `controller-gen`, no kustomize, and no Makefile-driven
build/deploy/e2e/lint pipeline for this project.

## Consequences

**Positive**
- Every file in the repo is one that was written and can be explained
  line-by-line — this is the point of the grading criterion.
- No unused surface (`Dockerfile`, in-cluster `Deployment` manifests, RBAC
  `ClusterRole`s, CI workflows, devcontainer) sitting in the repo implying
  capabilities — containerized deploy, CI, an e2e suite — that were never
  built out or tested.
- The API group/version/kind only need to agree across two files
  (`types.go`'s `GroupVersion` var and `crd.yaml`'s `group`/`versions`),
  instead of the several kubebuilder generates into (`PROJECT`,
  `groupversion_info.go`, CRD YAML, RBAC YAML, sample YAML).

**Negative / accepted trade-offs**
- No automatic sync between the Go `Spec`/`Status` structs and the CRD's
  OpenAPI schema — adding or renaming a field means hand-editing `crd.yaml`
  to match, with nothing to catch drift. Accepted: the schema is three
  fields today and changes are expected to be rare and easy to review by eye
  at this size.
- `DeepCopy`/`DeepCopyInto`/`DeepCopyObject` are hand-written rather than
  generated. Accepted for the same reason — both types are currently
  reference-free (no slices/maps/pointers in `Spec`/`Status`), so the
  hand-written copy is straightforward; revisit if either struct grows a
  reference-typed field.
- No RBAC `ClusterRole`, `Dockerfile`, or in-cluster `Deployment` path. If
  this operator ever needed to run inside the cluster instead of locally,
  that path would need to be built from scratch. Accepted because the
  README designates local execution as sufficient and expected.
- Diverges from the standard kubebuilder project layout a reviewer familiar
  with the tool might expect. Accepted as the deliberate trade against
  "200 lines you can defend."

## Alternatives considered

- **kubebuilder default scaffold** — rejected: generates CI, devcontainer,
  e2e, metrics/Prometheus, and deploy tooling irrelevant at this scale.
- **Manual scaffold (chosen)** — smallest surface area, matches the
  README's "run locally, no container" guidance exactly, every line
  self-authored.
